## Frida Monitor 是什么?

Frida 是一个动态插桩框架，可以在运行时把 JavaScript 注入到应用进程，Hook 任意 Java/Native 方法，拦截调用参数、返回值和调用栈。

HMDroidbot 的 monitor.py 利用它在 DroidBot 做 UI 探索的同时，同步监控应用调用了哪些敏感 API。

## 整体工作流
```log
DroidBot 驱动 UI 事件
        ↓
  应用执行某段代码
        ↓
  触发被 Hook 的 Java API
        ↓
  Frida 脚本捕获 → send(消息) → Python on_message 回调
        ↓
  记录到 sensitive_api / interested_api / method_stack
```

# deplay的功能

`deploy()` 的含义是：**在正式开始 UI 探索之前，向设备预置一套"测试环境数据"**，让被测应用启动后能遇到真实数据而不是空设备。


## 具体做了什么

`AppEnvManager.deploy()` 按策略生成一组 `AppEnv` 对象，逐一调用每个 env 的 `deploy(device)` 方法，把数据写入设备：

```270:285:/Users/mac/workspace/HuaWei/HMDroidbot/droidbot/env_manager.py

        self.logger.info("Start deploying environment, policy is %s" % self.policy)
        if self.env_factory is not None:
            self.envs = self.generate_from_factory(self.env_factory)
        if self.envs is None:
            return
        for env in self.envs:

                break

        if self.device.output_dir is not None:
            out_file = open(os.path.join(self.device.output_dir, "droidbot_env.json"), "w")
```

| 类 | `deploy()` 实际操作 |
|---|---|
| `ContactAppEnv` | 向设备写入一条联系人（默认 Lynn / 1234567890） |
| `SettingsAppEnv` | 修改设备系统设置（如屏幕亮度） |

| `SMSLogEnv` | 模拟一条收/发短信记录 |
| `GPSAppEnv` | 持续推送虚假 GPS 坐标（动态，后台线程） |
| `DummyFilesEnv` | 推送一批假文档/图片文件到设备存储 |


## 三种策略

| 策略 | 行为 |
|---|---|
| `none`（默认） | 跳过，不预置任何数据 |
| `dummy` | 六种数据全部预置一遍 |
| `static` | 根据 APK 静态分析的权限按需预置——例如应用声明了 `READ_CONTACTS` 才写联系人，声明了 `ACCESS_FINE_LOCATION` 才推 GPS |


## 为什么需要 deploy

很多应用启动后会立刻读联系人列表、展示通话记录、请求定位——如果设备是空的，这些界面就是空列表，DroidBot 的策略找不到可点击的内容，覆盖率就低。`deploy` 预先填充数据，让这些界面有内容可以探索。


**对于当前鸿蒙场景**：默认策略是 `none`，所以这步实际上是空操作，直接跳过。你在 `droidbot_env.json` 里看到的是一个空数组 `[]`，印证了这一点。

# 输入策略
**输入策略**是 DroidBot 的核心决策模块——它回答一个问题：**"当前界面该做什么操作？"**

每一步事件循环，`InputManager` 都调用策略的 `generate_event()` 方法，策略返回一个事件（点击、滑动、按键、启动 Intent…），然后发送给设备执行。


## 策略家族图

```
InputPolicy（抽象基类）
├── NoneInputPolicy          ← none：什么都不做
├── UtgBasedInputPolicy（抽象，维护 UTG）
│   ├── RandomPolicy         ← random：随机选
│   ├── UtgNaiveSearchPolicy ← dfs_naive / bfs_naive：朴素搜索
│   ├── UtgGreedySearchPolicy← dfs_greedy / bfs_greedy：贪心搜索（默认）
│   └── ManualPolicy         ← manual：人工操作录制
└── UtgReplayPolicy          ← replay：回放历史记录
（外部）MemoryGuidedPolicy    ← memory_guided（input_policy2.py）
（外部）LLM_Guided_Policy     ← llm_guided（input_policy3.py，当前不可用）
```

另外 `monkey` 和 `none` 不走 Python 策略层，直接在 `InputManager` 里处理。


## 各策略详解

### `dfs_greedy` / `bfs_greedy`（默认，推荐）
`UtgGreedySearchPolicy`，最智能的内置策略：

1. **优先点未探索过的控件**（`+explore`）
2. 当前页面全探索完后，在 UTG 里找一个**还有未探索事件的可达状态**，导航过去（`+navigate`）
3. 导航失败则重启应用
4. 重启次数过多则切换为随机模式
5. DFS 把 BACK 放列表末尾（深入优先），BFS 放列表开头（广度优先）

### `dfs_naive` / `bfs_naive`
`UtgNaiveSearchPolicy`，较早的简单版本：
- 维护 `explored_views` 集合，对未点过的控件逐一尝试
- 优先点 "ok / yes / allow / next" 等正向按钮
- 全部点过后尝试已知的状态转移路径，还没有就返回 None（重启应用）

### `random`
`RandomPolicy`：
- 获取当前界面所有可交互控件 → **随机选一个点**
- 不记录探索历史，不构建路径，纯概率覆盖

### `replay`
`UtgReplayPolicy`：
- 读取上次运行的 `output/events/*.json` 目录
- 按事件文件的 `start_state` 匹配当前界面状态
- 找到匹配的就重放那条事件，实现**确定性复现**

### `manual`
`ManualPolicy`：
- 不自动生成事件，等用户在终端按 Enter 保存当前界面状态
- 用于人工探索同时录制 UTG，供后续 replay 使用

### `monkey`
直接调用 `adb shell monkey`，绕过整个 Python 策略层（**仅 Android**）

### `none`
只启动应用，不发任何事件，用于静态观察

# Monkey 模式

Monkey 模式是 DroidBot 支持的一种**输入策略**（`-policy monkey`），它不走 DroidBot 自己的 Python 策略层，而是直接调用 Android 系统内置的 **`adb shell monkey`** 命令，把**事件生成**完全交给系统工具。

* 输入策略
输入策略运行在 Host 侧，它做的事是：
1. 从设备读状态：调用 hdc shell uitest dumpLayout 获取当前界面的控件树
2. 在 Python 里决策：分析哪些控件可点、哪些已探索过、下一步去哪
3. 向设备发事件：把决策结果通过 hdc shell uitest uiInput click x y 发给设备

* adb shell monkey
monkey 是 Android SDK 自带的压力测试工具，内置在 Android 设备的系统里（/system/bin/monkey）。它向目标应用发送大量随机的伪用户事件，用于发现应用崩溃、ANR（无响应）等稳定性问题。

最简单的一条命令：

adb shell monkey -p com.example.app 1000

向 com.example.app 发送 1000 个随机事件。

### 与其他策略的对比

| 维度 | Monkey | dfs_greedy / random 等 |
|---|---|---|
| 事件生成者 | 系统 `adb monkey` 进程 | DroidBot Python 策略层 |
| 事件类型 | 完全随机（触摸/滑动/按键） | 基于 UI 状态树定向生成 |
| 是否构建 UTG | 否 | 是 |
| 崩溃处理 | `--ignore-crashes` 自动忽略 | 依赖策略实现 |
| 适用场景 | 快速压力测试、崩溃发现 | 系统性 UI 覆盖探索 |

### 重要限制

**不支持鸿蒙设备**，原因有三：
1. 命令写死用 `adb`，鸿蒙设备走 `hdc`，不在 `adb` 设备列表里
2. `shell monkey` 是 Android 专属工具，鸿蒙系统没有这条命令
3. 代码里引用的是 Android `Device` 对象的 `serial` 属性，鸿蒙用的是 `DeviceHM`

**鸿蒙设备上想做随机压力测试**，应使用 `-policy random`，它通过 `hdc` 发送事件，完全兼容鸿蒙。
